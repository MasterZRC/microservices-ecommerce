# 电商微服务推荐系统核心流程详解

---

## 第一章 推荐系统概述与技术选型

### 1.1 问题背景与技术挑战

电子商务平台的商品规模动辄数以亿计，用户在海量商品中发现自己感兴趣内容的难度随商品规模的扩大而急剧增加。个性化推荐系统作为解决信息过载问题的核心技术，已经成为各大电商平台提升用户体验和平台收益的关键基础设施。一个设计良好的推荐系统不仅能够将用户从"大海捞针"式的商品搜索中解放出来，还能通过精准匹配用户兴趣来提升商品的曝光转化率，从而带来可观的商业价值。

然而，工业级推荐系统面临着一系列独特的技术挑战。第一，**规模问题**——需要在数十万乃至数百万量级的商品池中，为每个用户快速返回个性化的推荐结果，这对系统的计算能力和响应延迟都提出了极高的要求。第二，**效果问题**——推荐结果需要尽可能准确，既不能推荐用户完全不感兴趣的商品（损害体验），也不能推荐过于同质化的商品（降低新颖性和多样性）。第三，**实时性问题**——用户的兴趣是动态变化的，推荐系统需要能够感知用户兴趣的变化并在推荐结果中及时反映。第四，**冷启动问题**——新用户缺乏历史行为数据、新商品缺乏交互记录，如何为这些"缺乏数据"的场景提供有效的推荐，是一个经典难题。

### 1.2 两阶段推荐范式

业界解决上述挑战的标准方案是**两阶段推荐范式**，即"召回（Recall）+ 排序（Rank）"的分阶段设计。

**召回阶段**的核心任务是从全量商品中快速筛选出一个较小的候选集（通常几十到上百个商品）。召回阶段需要在"广"字上下功夫——尽可能覆盖用户可能感兴趣的各个方向，保证推荐的多样性和新颖性。由于需要从数十万商品中筛选，召回阶段通常采用相对轻量级的算法（如协同过滤、热门策略等），单次召回的延迟必须控制在毫秒级。

**排序阶段**则是在召回阶段产生的候选集上，利用更复杂的模型和更丰富的特征进行精细化的点击率（CTR）预估，按预测分数从高到低排序，分数越高的商品意味着用户越可能点击，因此排在推荐列表越靠前的位置。排序阶段追求的是"准"字——在较小的候选集上充分挖掘用户与商品之间的深层关系。

两阶段范式的核心价值在于计算效率与推荐效果的平衡。直接对全量商品使用复杂模型进行排序是不现实的——计算量过大、延迟不可接受；而仅使用轻量级召回算法则无法充分利用复杂的用户-商品交互模式。通过将"广覆盖"和"精排序"分离，各自在合适的规模上使用合适的算法，实现了效率与效果的兼顾。这一设计范式已被各大厂的推荐系统广泛采用，包括 YouTube 的视频推荐、淘宝的商品推荐等。

### 1.3 微服务架构选型

本项目采用微服务架构设计推荐系统，将推荐功能拆分为多个独立部署、独立扩展的服务单元。相比于传统的单体架构，微服务架构的优势在于：各服务之间松耦合，可以独立迭代和部署；不同服务可以根据其计算特征选择最合适的技术栈；系统的弹性扩展能力更强，热门商品召回压力大时可以单独扩容 recommendation-service，深度学习排序计算密集时可以单独扩容 recommendation-rank-service。

整个推荐系统由以下核心微服务组成：**API Gateway**（统一流量入口，负责 JWT 认证和路由转发）；**recommendation-service**（Java Spring Boot，推荐业务主服务，协调召回、排序、后处理等全流程）；**recommendation-rank-service**（Python FastAPI，独立的深度学习 CTR 预估排序服务）；**product-service**（Java Spring Boot，商品数据服务）；**user-service**（Java Spring Boot，用户管理服务）。

基础设施层面：**Nacos v2.3.0** 提供服务注册发现和动态配置能力；**MySQL 8.0** 作为关系型数据主存储；**Redis 7.2** 承担缓存、消息队列（Redis Stream）、A/B 测试指标统计等多重角色；**Docker Compose** 实现容器化一键部署。

## 第二章 推荐完整流程详解

当用户在电商平台的客户端（Web 页面或 App）点击"为你推荐"模块时，推荐系统将经历以下七个步骤的完整处理链路。以下逐章深入分析每个步骤的技术细节与设计考量。

### 2.1 步骤一：用户请求路由与身份认证

#### 2.1.1 请求入口与负载均衡

用户在前端发起的推荐请求格式如下：

```
GET /api/recommendation/personal/products?userId=123&limit=32
```

该请求首先经过负载均衡器（如 Nginx 或云厂商的 SLB）转发至 API Gateway 集群（端口 8080）。API Gateway 基于 Spring Cloud Gateway 实现，是整个系统的唯一外部流量入口。所有面向客户端的请求都必须经过网关，这一设计避免了各下游业务服务直接暴露在公网中。

#### 2.1.2 JWT Token 认证流程

网关的第一项核心职责是**JWT（JSON Web Token）身份认证**。JWT 是一种基于 Token 的开放标准（RFC 7519），其核心思想是：服务端不再依赖 session 来存储用户登录状态，而是将用户的身份信息加密签名为一个 Token，客户端每次请求时携带此 Token，服务端通过验证 Token 的签名来确认用户身份。

一个 JWT Token 由三部分组成，各部分之间用点号（.）分隔：**Header（头部）**——包含 Token 类型和签名算法（如 HS256）；**Payload（载荷）**——包含用户声明（如 userId、expireTime 等）；**Signature（签名）**——对前两者的加密签名，防止数据被篡改。

网关的 `JwtAuthenticationFilter` 拦截所有请求，执行以下验证流程：

**第一步：从请求头中提取 Token**。客户端在 HTTP 请求头中以 `Authorization: Bearer <token>` 的格式携带 Token，过滤器从中解析出 token 字符串。

**第二步：验签**。网关使用预置的 secret key 对 Token 的 Header 和 Payload 进行 HMAC-SHA256 签名，将结果与 Token 中携带的 Signature 进行比对。如果两者不一致，说明 Token 被人为篡改，请求立即被拒绝。

**第三步：过期检查**。Token 的 Payload 中包含 `exp`（Expiration Time）字段，记录 Token 的过期时间戳。如果当前时间已超过该时间戳，说明登录已过期，请求同样被拒绝。

**第四步：用户身份提取**。验签和过期检查都通过后，过滤器从 Payload 中解析出用户的唯一标识符 `userId`。

#### 2.1.3 内部安全 Header 注入机制

认证通过后，网关将解析得到的真实 `userId` 写入一个**自定义 HTTP Header**——`X-Authenticated-User-Id`——中，然后继续向后转发请求。

这一设计的核心价值在于安全性保障。请注意整个流程中一个容易被忽视但至关重要的细节：**推荐接口的 userId 参数来自网关从 Token 中解析的值，而非来自客户端传入的 URL 参数**。其代码逻辑如下：

```java
@GetMapping("/personal/products")
public ResponseEntity<Map<String, Object>> getPersonalizedRecommendationProducts(
        @RequestHeader(value = "X-Authenticated-User-Id", required = false) Long authUserId,
        @RequestParam Long userId,
        @RequestParam(defaultValue = "10") Integer limit) {

    // 始终使用经过网关认证的 Header，防止用户伪造身份
    Long verifiedUserId = (authUserId != null) ? authUserId : userId;

    List<Map<String, Object>> products =
        recommendationService.getPersonalizedProductDetails(verifiedUserId, limit);

    return ResponseEntity.ok(Map.of("userId", verifiedUserId, "products", products));
}
```

如果客户端传入的 URL 参数 `userId=456`，但 Token 中解析出的实际 userId 是 `123`，网关将优先使用 `123` 作为认证身份。这意味着即使用户试图通过修改 URL 参数来查询他人的推荐结果，请求也会被正确地以自己的身份处理，从根本上杜绝了身份伪造的可能。

#### 2.1.4 路由转发

认证和 Header 注入完成后，网关根据请求路径中的服务标识（`/api/recommendation/**`）将流量转发至 `recommendation-service` 的内部地址（`http://recommendation-service:8004`）。由于网关和下游服务均部署在同一个 Docker 网络中，这一步是内网通信，延迟极低。

### 2.2 步骤二：多路召回（Multi-Channel Recall）

#### 2.2.1 召回阶段的设计目标与核心思想

召回（Recall）是整个推荐链路的第一层过滤环节，其核心目标是从全量商品中快速筛选出一个与用户相关的候选集合。与排序阶段追求的"精准"不同，召回阶段追求的是**"广覆盖"**——候选集应该尽可能多地涵盖用户可能感兴趣的各个方向，既要包含用户明确表达过偏好的类目，也要包含用户可能感兴趣但尚未探索的新类目。

为什么需要在排序之前设置召回层？假设系统有 100 万商品，直接对全部商品使用 DeepFM 排序，单次请求的计算量将极其庞大——假设每个商品的特征处理耗时 1ms，100 万商品就需要约 1000 秒，显然不可接受。通过召回层将候选规模从 100 万压缩到 100 左右，排序阶段的计算量就变得可以接受了：100 个商品 × 1ms = 0.1 秒，加上网络通信开销也能控制在 1 秒以内。

本系统设计了四条互补的召回通道：**ItemCF 协同过滤召回**、**热门商品召回**、**同类目热门召回**和**基于 TF-IDF 的内容相似度召回**。四条通道从不同的角度挖掘用户的潜在兴趣，相互补充、相互兜底。

#### 2.2.2 通道一：基于物品的协同过滤（ItemCF）

**协同过滤**（Collaborative Filtering，CF）是推荐系统领域历史最悠久、应用最广泛的算法之一。其核心哲学是"物以类聚，人以群分"——如果大量用户对商品 A 和商品 B 都表现出了相似的偏好（都购买、都加购），那么喜欢商品 A 的用户很可能也会喜欢商品 B。

协同过滤分为**基于用户的协同过滤（UserCF）**和**基于物品的协同过滤（ItemCF）**两种。在电商场景下，由于用户数量远大于商品数量（百万用户 vs 十万商品），ItemCF 的相似度矩阵规模更小、计算效率更高、且物品的稳定性和可解释性更好（商品不会像用户那样频繁改变偏好），因此本系统采用 ItemCF 方案。

##### 2.2.2.1 用户-物品加权交互矩阵的构建

ItemCF 召回的第一步是构建用户-物品的加权交互矩阵。系统的行为数据来源于 MySQL 的 `user_behavior` 表，该表记录了用户对商品的各种操作行为。

不同行为类型反映了用户对商品不同程度的兴趣强度。直观地分析：购买（buy）是转化信号最强的行为，代表用户已经完成了决策；加购（cart）表示用户有明确的购买意向但尚未付款；收藏（favorite）表示用户对商品有较强的兴趣和认可；点击（click）表示用户主动注意到了该商品并产生了兴趣；浏览（view）则是一种较弱的兴趣信号，可能是用户无意间看到的。因此，这些行为需要被赋予不同的权重：

| 行为类型 | 权重值 | 设计考量 |
|---------|--------|---------|
| 购买（buy） | 8 | 最强购买意向，转化信号最明确 |
| 收藏（favorite） | 5 | 明确的偏好信号 |
| 加购（cart） | 4 | 购买意向强烈 |
| 点击（click） | 2 | 一定兴趣 |
| 浏览（view） | 1 | 基础兴趣信号 |

然而，仅考虑行为类型权重还不够。用户三个月前的浏览行为对当前推荐的参考价值显然不如今天的浏览行为。因此，系统引入了**时间衰减因子**（decay factor），使近期行为的权重更高，远期行为的权重逐渐降低：

$$
\text{recencyWeight} = \text{decayFactor}^{\text{daysAgo}}
$$

其中 `decayFactor = 0.95`（可配置），`daysAgo` 是行为距离今天的天数。例如：

- 当天的购买行为：权重 $= 8 \times 0.95^0 = 8.0$
- 7 天前的加购行为：权重 $= 4 \times 0.95^7 \approx 4 \times 0.698 = 2.79$
- 30 天前的浏览行为：权重 $= 1 \times 0.95^{30} \approx 1 \times 0.215 = 0.215$

可以看到，30 天前的浏览行为对推荐的贡献已经衰减到原值的 21.5%，这符合用户兴趣随时间衰减的直觉。

最终，每条行为记录的得分为 $score = baseWeight \times recencyWeight$。系统从 MySQL 中加载最近 50,000 条行为记录，为每个用户汇总其在各类商品上的加权得分，形成用户-物品加权交互矩阵。

##### 2.2.2.2 物品相似度矩阵的计算

得到加权交互矩阵后，需要计算任意两个物品之间的相似程度。本系统采用**加权余弦相似度**算法。

**共现加权值的计算**：物品 $i$ 和物品 $j$ 的共现加权值 $c_{ij}$ 定义为：所有同时与物品 $i$ 和物品 $j$ 产生过交互的用户 $u$，对其交互得分进行加权求和：

$$
c_{ij} = \sum_{u \in U(i) \cap U(j)} \text{userPenalty}_u \times \text{score}_{u,i} \times \text{score}_{u,j}
$$

其中 $\text{userPenalty}_u = 1 / \log(1 + |I_u|)$ 是对活跃用户的降权处理，$|I_u|$ 是用户 $u$ 交互过的商品总数。这一惩罚的逻辑是：如果一个用户与大量商品都产生了交互（可能是刷单、数据爬取或深度浏览型用户），其行为数据的"纯度"较低，对相似度计算的贡献应该被适当降低。对数函数的设计确保了惩罚力度与用户活跃度的增长不成正比——活跃度翻倍，惩罚并不会翻倍。

**余弦相似度公式**：物品 $i$ 和物品 $j$ 的最终相似度为：

$$
\text{sim}(i, j) = \frac{c_{ij}}{||V_i|| \times ||V_j||}
$$

其中 $||V_i||$ 和 $||V_j||$ 分别是物品 $i$ 和物品 $j$ 的向量模长。分母的归一化处理确保了相似度值在 $[0, 1]$ 范围内（由于权重均为正值，实际范围在 [0, 1]）。

**类目加成机制**：`category_bonus = 1.2`（同类目）× `1.0`（不同类目）。即同属一个类目的商品在计算相似度时会获得 20% 的加权加成。这是因为类目相同往往意味着商品在功能或用途上相近（如同为"手机类目"的两款手机），用户对其中一件商品的偏好确实可以迁移到另一件上。

**热门惩罚机制**：`hot_penalty = 1 / \log(10 + (pop_i + pop_j) / 2)`。这是解决**热门偏差**问题的关键设计。在协同过滤中，如果某个商品是爆款（如 iPhone），几乎所有用户都与它产生过交互，那么其他所有商品与 iPhone 的共现值都会很高，导致"所有商品都与 iPhone 高度相似"这一错误结论。通过对热门商品的相似度进行对数惩罚，可以有效抑制这种偏差。

相似度矩阵的计算结果被缓存至 Redis，缓存键为 `recommendation:similarity:v1:all`，TTL = 24 小时。下次计算时优先从缓存读取，只有缓存失效时才重新计算。

##### 2.2.2.3 推荐得分的计算

得到物品相似度矩阵后，为用户推荐商品的得分计算公式为：

$$
\text{score}(user, \text{item}_k) = \sum_{\text{item}_i \in \text{History}(user)} \text{historyScore}_i \times \text{sim}(\text{item}_i, \text{item}_k)
$$

直观理解：遍历用户历史交互过的所有商品 $\text{item}_i$，将用户对该商品的加权得分 $\text{historyScore}_i$（包含行为权重 × 时间衰减）与 $\text{item}_i$ 和候选商品 $\text{item}_k$ 之间的相似度 $\text{sim}(\text{item}_i, \text{item}_k)$ 相乘并求和。得分越高，说明候选商品 $\text{item}_k$ 与用户整体兴趣越匹配。

系统取得分最高的 `cfRecallCount = 80` 个商品作为 ItemCF 召回通道的输出。

##### 2.2.2.4 增量 ItemCF 的优化

传统 ItemCF 存在一个痛点：当用户产生新行为时，需要重新计算全量相似度矩阵。设商品数量为 $n$，相似度矩阵的存储空间为 $O(n^2)$，每次更新的计算复杂度也是 $O(n^2)$。当商品规模达到十万级别时，$O(n^2)$ 的计算量将非常惊人。

本系统通过 `IncrementalItemCFService` 实现了**增量更新优化**，将计算复杂度从 $O(n^2)$ 降低到了 $O(n \cdot k)$，其中 $k$ 是每个商品的平均邻居数量（通常远小于 $n$）。

增量更新的设计思想是：当用户与某商品产生新交互时，只需更新与该商品相关的局部相似度，而非全量重算。具体流程如下：

```
触发时机：用户产生新行为时自动触发
处理逻辑：
  1. 获取该商品的相似商品列表（从主相似度矩阵中查询）
  2. 计算相似度增量
     increment = baseIncrement(0.01) + weightBonus(行为权重 × 0.001)
  3. 将增量写入独立的 Redis 增量矩阵（键名: recommendation:similarity:increment:{version}）
     增量矩阵独立于主矩阵，避免污染
  4. 定时合并任务（每5分钟执行一次）：
       - 读取所有增量矩阵
       - 将增量累加到主矩阵对应位置
       - 更新矩阵版本号
       - 清空已合并的增量矩阵
```

增量的累加公式为 $\text{new\_sim}(i, j) = \text{old\_sim}(i, j) + \text{increment}$。增量值的设计考虑了行为类型——购买行为的增量（$0.01 + 8 \times 0.001 = 0.018$）大于浏览行为的增量（$0.01 + 1 \times 0.001 = 0.011$），确保购买行为对相似度的影响更大。

##### 2.2.2.5 冷启动用户的 ItemCF 兜底

如果用户的历史行为记录极少（少于 5 条），ItemCF 的相似度计算可能不够可靠。系统对这类用户采用**降级策略**：当 ItemCF 召回结果少于 20 个商品时，自动补充热门商品召回的结果作为补充。

#### 2.2.3 通道二：热门商品召回

热门商品召回是最简单但也最稳健的召回策略之一。其核心思想是"跟着大众的选择走"——如果一个商品被大量用户购买、加购或浏览，说明该商品具有普遍吸引力，推荐给当前用户通常不会出错。

**算法设计**：

$$
\text{popularScore}(\text{item}) = \sum_{\text{behavior} \in \text{all\_behaviors\_of\_item}} \text{baseWeight}(\text{behavior}) \times \text{decayFactor}^{\text{daysAgo}}
$$

与 ItemCF 类似，热门召回同样引入了时间衰减因子，确保**近期**表现热门的商品排名更靠前。例如，一件一周前爆卖但本周已降温的商品，其得分应该低于本周新晋热卖的商品。这一设计保证了推荐结果能够跟随商品热度的变化而动态更新。

热门召回同样被缓存至 Redis（`recommendation:popular:decay-0.95:all`，TTL = 1 小时）。当 `user_behavior` 表中没有数据时（如系统刚上线阶段），系统会 fallback 到 `product-service` 按商品的 `sales`（销量）字段查询真实销量数据作为兜底。

#### 2.2.4 通道三：同类目热门召回

同类目召回基于一个朴素的假设：**用户对其偏好的类目具有持续的兴趣**。如果用户在近期大量浏览和购买了某一类目的商品，说明该用户对该类目有明确的偏好，那么该类目下的其他热门商品同样值得推荐。

**用户偏好类目的计算**是这一召回通道的核心。系统通过分析用户最近 500 条行为记录，结合每条记录的行为权重和时间衰减，计算用户对各商品类目的综合得分：

$$
\text{categoryScore}(\text{category}) = \sum_{\text{behavior} \in \text{userHistory}} \text{weight}(\text{behavior}) \times \text{decayFactor}^{\text{daysAgo}} \quad (\text{only for items in this category})
$$

得分最高的类目即被确定为用户的**偏好类目**（preferredCategory）。在推荐时，系统从该偏好类目中获取热门商品作为候选。

**智能补充策略**：系统采用了一种混合比例——70% 的候选商品来自用户偏好类目，30% 来自其他类目。这一设计的考量是：大部分推荐应该来自用户感兴趣的类目（保证相关性），但也需要给予用户探索新类目的机会（保证多样性）。

#### 2.2.5 通道四：基于 TF-IDF 的内容相似度召回

**基于内容的召回**（Content-Based Filtering，CBF）是协同过滤的重要补充手段。协同过滤依赖用户-商品的交互数据，因此对于**冷启动**场景（新用户无历史行为、新商品无被交互记录）天然失效。基于内容的召回则通过分析商品本身的属性特征（如标题文本、类目、品牌等）来计算商品间的相似性，不依赖于用户行为数据。

本系统的内容召回基于**商品标题的 TF-IDF（Term Frequency-Inverse Document Frequency）向量相似度**计算。TF-IDF 是一种经典的文本特征提取方法，它评估一个词在单个文档中的重要性——一个词在当前文档中出现越多越重要（TF 高），但在所有文档中出现越多则越不重要（IDF 低）。

##### 2.2.5.1 中文分词与 N-gram 处理

与英文不同，中文文本没有天然的分词边界（词与词之间没有空格分隔），因此需要借助分词工具。本系统采用**字符级 N-gram 分词**策略而非词典分词，其核心步骤如下：

**输入**："无线蓝牙耳机 5.0 降噪版"

**第一步：字符清洗与过滤**。去除标点符号和数字，得到字符序列："无线蓝牙耳机降噪版"。

**第二步：N-gram 词元提取**。系统采用 2-gram 和 3-gram 混合策略，每次取连续 2 或 3 个字符作为一个词元（token）：

```
2-gram: 无线, 线蓝, 蓝牙, 牙耳, 耳机, 频降, 降噪, 噪版
3-gram: 无线蓝, 线蓝牙, 蓝牙耳, 牙耳机, 频降噪, 降噪版
```

**第三步：停用词过滤**。使用停用词表过滤掉"的、了、和、是、的、在、有、等、与"等无实际意义的常见词。

**第四步：词频统计**。统计每个词元在该商品标题中出现的次数。

这种 N-gram 策略的优势在于：无需依赖外部词典，分词粒度可控，能够捕捉到短语级别的语义（如"无线蓝"包含了"无线"和"蓝牙"两个词的组合信息）。

##### 2.2.5.2 TF-IDF 向量构建

对于每个商品的标题，构建其 TF-IDF 向量：

$$
\text{TF}(t, d) = \frac{\text{词 } t \text{ 在文档 } d \text{ 中出现的次数}}{\text{文档 } d \text{ 的总词数}}
$$

$$
\text{IDF}(t) = \log\left(\frac{N + 1}{\text{df}(t) + 1}\right) \quad \text{// 平滑处理避免 df=0 时除零}
$$

$$
\text{TF-IDF}(t, d) = \text{TF}(t, d) \times \text{IDF}(t)
$$

IDF 公式中的平滑处理（分子分母各加 1）确保即使某个词在所有文档中都出现（$\text{df} = N$），其 IDF 值也不会变成负无穷（因为 $\log((N+1)/(N+1)) = \log(1) = 0$）。

举例说明：假设全平台有 10,000 个商品（$N = 10000$）。词"耳机"出现在 3,000 个商品标题中（$\text{df} = 3000$），其 $\text{IDF} = \log(10001/3001) \approx 1.20$。词"骁龙888"仅出现在 50 个商品标题中（$\text{df} = 50$），其 $\text{IDF} = \log(10001/51) \approx 5.30$。可以看到，"骁龙888"这个专有名词的 IDF 值远高于"耳机"，说明它具有更强的商品区分能力——搜索"骁龙888"的用户目标远比搜索"耳机"的用户更加明确。

##### 2.2.5.3 用户兴趣画像构建

将用户历史浏览/点击过的所有商品的 TF-IDF 向量进行**MM（Maximum Matching，最大匹配）池化**聚合，形成用户的兴趣画像向量：

$$
\text{userProfile}[t] = \max_{\text{item} \in \text{userHistory}} \text{TF-IDF}(\text{item}, t)
$$

即取各维度上的最大值，而非简单平均（均值池化）或求和。例如，假设词"降噪"在用户浏览过的商品 A 中 TF-IDF = 0.8，在商品 B 中 TF-IDF = 0.2，在商品 C 中 TF-IDF = 0.5，则用户画像中"降噪"维度的值为 $\max(0.8, 0.2, 0.5) = 0.8$。

**MM 池化相对于均值池化的优势**在于：均值池化会稀释掉用户最强烈的兴趣特征——如果用户浏览了 10 件商品，其中 1 件是"降噪耳机"（TF-IDF = 0.8），其余 9 件都与"降噪"无关（TF-IDF = 0），均值池化会将这一维度的值拉低到 $0.8 / 10 = 0.08$，掩盖了用户对"降噪"功能的强烈偏好。MM 池化则保留了峰值，确保用户的核心兴趣不会被稀释。

##### 2.2.5.4 余弦相似度与候选生成

计算候选商品与用户兴趣画像之间的**余弦相似度**：

$$
\cosineSimilarity(A, B) = \frac{A \cdot B}{||A|| \times ||B||}
$$

余弦相似度的取值范围是 $[-1, 1]$，由于 TF-IDF 向量各维度均为非负值，实际范围在 $[0, 1]$ 之间。相似度越接近 1，说明候选商品的标题与用户的历史偏好越匹配。

返回相似度最高的 Top-K 个商品作为内容召回结果。这一召回通道的主要作用是应对冷启动场景。当一个用户的历史行为非常稀少时，ItemCF 的相似度计算可能不够可靠，此时基于这些少量商品的标题内容找到语义相似的新商品，可以作为有效的补充推荐。

#### 2.2.6 多路召回的分层合并策略

四条召回通道各自独立运行后，需要合并成一个统一的候选集。系统的合并策略遵循**质量优先、分层插入**的原则：

```
合并流程：
  1. 首先加入 ItemCF 召回商品（基于用户真实历史行为，相关性最强）
  2. 按分数降序依次插入同类目召回商品（权重×2）和热门召回商品（权重×1）
  3. 内容召回候选作为兜底补充（应对冷启动）
  4. 最终最多保留 maxPoolSize = 120 个商品
```

合并过程中还需要对各通道的结果进行**差异化过滤**：

- **ItemCF 召回**：只过滤用户已**购买**的商品（已购买说明需求已被满足），但**保留**用户已加购/已收藏的商品（用户已加购说明仍有购买意向，可能因价格等原因尚未付款，推荐同类商品有机会促成转化）
- **同类目召回**：同样只过滤已购买商品
- **热门召回**：过滤已购买和已加购/已收藏的商品（热门商品如果用户已经加购，说明已有明确购买意向，此时推荐同类热门商品属于重复推荐，效果不佳）

这种差异化过滤策略体现了对用户不同行为意向的精细化理解和区分。

### 2.3 步骤三：灰度分流与 A/B 测试

在进入排序阶段之前，系统通过**灰度发布**（Gray Release）机制决定是否为当前用户启用深度学习排序模型。这一机制的核心价值在于：允许新算法在受控范围内（少量用户）上线试运行，通过实时采集的 A/B 测试数据评估其实际效果，只有效果显著优于旧算法时才会逐步扩大灰度比例直至全量。

#### 2.3.1 灰度分组的原理

灰度分组的本质是一个**用户分组算法**。本系统采用一致性哈希（Consistent Hashing）的简化实现：

```java
boolean isGrayUser = (hash(userId) % 100) < grayRatio;
```

其中 `grayRatio` 默认设置为 10，意味着约 10% 的用户被分入**灰度组**（使用 DeepFM 排序），90% 的用户留在**对照组**（使用原始 ItemCF 排序后直接进入后处理，跳过 DeepFM 排序步骤）。

**为什么用 hash 而不是直接取模？**假设 `userId` 从 1 开始递增，如果直接对 `userId % 100` 判断，则 userId 1-10 的用户全部命中灰度组，userId 11 及之后的用户全部命中对照组——分组在用户空间中严重不均匀。使用 `hash(userId) % 100`（Java 中 hashCode 对字符串/数值的哈希值相对均匀分布）可以确保分组结果在用户 ID 空间上均匀分布。

**一致性保证**：分组结果会被缓存至 Redis（键名：`gray:user:{userId}`），TTL = 7 天。这意味着同一个用户在 7 天内将始终命中同一分组。如果用户每次访问推荐页面的分组结果都不同（今天是灰度组，明天是对照组），其看到的推荐结果会产生显著差异，严重影响用户体验。一致性分组保证了用户体验的稳定性。

#### 2.3.2 A/B 指标的实时记录

系统使用 Redis 的 **HyperLogLog** 数据结构记录各组的 A/B 测试指标。HyperLogLog 是一种概率计数算法，能够用极少的内存（约 12KB）实现独立访客人数的统计，误差率约为 0.81%，对于数十万量级的 A/B 测试场景完全足够。

记录的指标包括：

| 指标类型 | 记录时机 | 用途 |
|---------|---------|------|
| 曝光（exposure） | 推荐结果展示给用户 | 计算 CTR 的分母 |
| 点击（click） | 用户点击推荐商品 | 计算 CTR 的分子 |
| 加购（cart） | 用户将推荐商品加入购物车 | 计算加购率 |
| 下单（order） | 用户通过推荐商品完成购买 | 计算下单率和 GMV |

每类指标的存储键包含日期维度（如 `gray:exposure:20260328:gray`），每日独立统计，支持按日环比分析趋势变化。每日指标的 TTL = 8 天，保证 7 天以上实验周期内的历史数据都能被查询。

#### 2.3.3 指标对比与决策

基于上述记录，系统可以实时计算并对比灰度组（DeepFM）和对照组（ItemCF）的核心业务指标：

$$
\text{CTR} = \frac{\text{click\_count}}{\text{exposure\_count}}
$$

$$
\text{加购率} = \frac{\text{cart\_count}}{\text{exposure\_count}}, \quad \text{下单率} = \frac{\text{order\_count}}{\text{exposure\_count}}
$$

$$
\text{GMV提升} = \frac{\text{灰度组人均GMV} - \text{对照组人均GMV}}{\text{对照组人均GMV}} \times 100\%
$$

在评估新算法效果时，通常需要观察至少 7 天的数据以确保结果具有统计显著性。同时需要注意，DeepFM 的优势可能需要一定的数据积累才能体现——模型需要学习到足够的用户-商品交互模式后，才能在排序准确性上超越简单的 ItemCF 分数排序。

### 2.4 步骤四：DeepFM 精排（Rerank）

#### 2.4.1 CTR 预估问题的定义

**点击率预估**（Click-Through Rate Prediction）是推荐系统和广告系统中最核心的机器学习问题之一。CTR 预估的任务是预测用户点击某个商品的概率 $P(\text{click} | \text{user}, \text{item})$。准确预测这一概率不仅关系到推荐结果的相关性——用户点击了推荐商品说明推荐有效，还直接影响平台的广告收入（广告按点击计费，CPM/CPC 计费模式）和商品转化率。

CTR 预估问题可以形式化为一个二分类问题：给定用户特征 $X_u$ 和商品特征 $X_i$，预测用户点击商品的概率 $P(\text{click}=1 | X_u, X_i)$。模型的输出是一个 0 到 1 之间的概率值，概率越接近 1，说明用户越可能点击该商品。

CTR 预估面临以下核心挑战：

**特征维度高且稀疏**。用户 ID、商品 ID、类目 ID、品牌 ID 等都是高维的稀疏特征（类别型特征）。直接将这些 ID 作为特征输入模型会遇到维度灾难问题（one-hot 编码后维度等于 ID 数量）。解决方案是**Embedding**技术——将高维稀疏的 ID 映射为低维稠密的向量，类似于 Word2Vec 的思想。

**特征交叉隐含在高维空间中**。用户是否点击某商品，往往取决于多个特征之间的组合效果。例如"男性用户 + 高端品牌 + 电子产品"这种特定组合可能会显著提升点击率——这是一个涉及三个特征的三阶交互。仅靠人工设计（手动枚举所有可能的交叉特征）是不可能穷尽的：一阶特征有 10 个，二阶交互就有 $C(10,2) = 45$ 个，三阶交互有 $C(10,3) = 120$ 个，特征工程的工作量将指数级爆炸。

**需要同时捕捉低阶和高阶特征交互**。低阶交互（如用户年龄和商品价格各自独立的影响，以及用户偏好类目是否与商品类目匹配的二阶交互）和高阶交互（多层神经网络隐层中自动学习到的深层组合模式）都很重要。人工设计难以同时覆盖这两类交互。

**DeepFM**模型正是为解决这些问题而设计的。

#### 2.4.2 特征工程

CTR 预估模型的效果高度依赖于特征工程的质量。本系统的特征分为用户特征和商品特征两大类，全部从真实数据源中获取。

**用户特征**通过查询 MySQL 数据库获取：

```
行为统计特征：
  - 近1天浏览/点击/加购/购买次数（view_1d, click_1d, cart_1d, buy_1d）
  - 近7天浏览/点击/加购/购买次数（view_7d, click_7d, cart_7d, buy_7d）
  - 最后活跃时间（距今天的小时数）

偏好特征：
  - 偏好类目 Top3（按购买/加购/收藏权重的加权得分排序）
  - 偏好品牌 Top2（按行为权重排序）
```

这些特征的设计逻辑是：行为统计特征刻画了用户的**近期活跃度**和**短期兴趣**（1 天内的高频行为反映即时需求），偏好特征则刻画了用户的**中长期偏好倾向**（偏好类目和品牌反映稳定的购物风格）。

**商品特征**通过调用 product-service 的 REST API 批量获取：

```
属性特征：
  - 类目ID（category_id）：商品的真实类目编号
  - 品牌哈希（brand_id）：品牌名通过 hashCode % 100 映射为 0-99 的整数
  - 价格分桶（price_bucket）：价格 / 100，取整数分桶
  - 销量分桶（sales_bucket）：销量 / 100，取整数分桶

统计特征：
  - 热门度分数（hot_score）：商品的累计销量
  - 价格比例（price_ratio）：price / 1000.0
```

商品特征通过批量查询接口 `POST /api/product/batch` 一次性获取（分页 pageSize=1000），避免了大量商品查询时的 N+1 问题。当批量接口不可用时，降级方案为逐个调用 `GET /api/product/{id}`。

#### 2.4.3 DeepFM 模型架构解析

DeepFM（Deep Factorization Machine）由华为诺亚方舟实验室于 2017 年提出（论文发表于 IJCAI 2017），其核心创新在于将**因子分解机（FM）**与**深度神经网络（DNN）**有机结合，同时学习**低阶特征交互**（FM 部分）和**高阶特征交互**（DNN 部分），且两者**共享输入层的 Embedding 表示**。

模型的输入层包含两类特征：**稀疏特征**（类别型特征，如类目 ID、品牌 ID、价格分桶等，经过 Embedding 后参与计算）和**密集特征**（数值型特征，如浏览次数、价格比例等，经过归一化处理后直接输入）。

**模型的 FM 组件**负责捕捉低阶特征交互，分为一阶和二阶两部分：

**一阶（First Order）**：对每个特征进行线性加权求和：

$$
\text{firstOrder} = \sum_{i=1}^{n} w_i \cdot x_i
$$

其中 $w_i$ 是特征 $x_i$ 的线性权重。这一层捕捉的是每个特征**单独**对点击率的影响。

**二阶（Second Order）**：捕捉所有特征**两两之间**的交互关系。传统的二阶交互需要 $O(n^2)$ 的计算复杂度，FM 通过一个巧妙的数学变换将其降低到 $O(n \cdot k)$：

$$
\text{secondOrder} = 0.5 \times \left[ \left( \sum_{i=1}^{n} V_i \cdot x_i \right)^2 - \sum_{i=1}^{n} (V_i \cdot x_i)^2 \right]
$$

其中 $V_i$ 是特征 $x_i$ 的 $k$ 维 Embedding 向量。关键的数学恒等变换推导如下：

设 $a_i = V_i \cdot x_i$（标量），则：

$$
\left( \sum_{i=1}^{n} a_i \right)^2 = \sum_{i=1}^{n} a_i^2 + 2 \times \sum_{1 \leq i < j \leq n} a_i \cdot a_j
$$

因此：

$$
\left( \sum_{i=1}^{n} a_i \right)^2 - \sum_{i=1}^{n} a_i^2 = 2 \times \sum_{1 \leq i < j \leq n} a_i \cdot a_j
$$

代入 secondOrder 公式得：

$$
\text{secondOrder} = 0.5 \times 2 \times \sum_{1 \leq i < j \leq n} \langle V_i, V_j \rangle \cdot x_i \cdot x_j = \sum_{1 \leq i < j \leq n} \langle V_i, V_j \rangle \cdot x_i \cdot x_j
$$

可以看到，最终的结果正是所有特征对的二阶交互之和。而计算过程中只需要：先求和（$O(n)$ 次向量加法），再平方（$O(k)$ 次乘法），最后减去向量的平方和（$O(n \cdot k)$ 次乘法），总复杂度为 $O(n \cdot k)$ 而非 $O(n^2 \cdot k)$。

**模型的 DNN 组件**负责捕捉高阶特征交互。DNN 由多个全连接层组成：

```
Input: 所有特征的 Embedding 向量拼接 → 维度 128
  ↓
Layer1: Linear(128→64) → BatchNorm → ReLU → Dropout(0.5)
  ↓
Layer2: Linear(64→32) → BatchNorm → ReLU → Dropout(0.5)
  ↓
Output: 32维向量
```

DNN 通过多层非线性变换，能够自动学习特征之间的深层交互模式，而这些交互模式往往难以通过人工枚举来覆盖。

**最终输出**：

$$
\text{output} = \sigma\left(\text{firstOrder} + \text{secondOrder} + \text{DNN\_output}\right)
$$

其中 $\sigma(\cdot)$ 是 sigmoid 函数，将输出映射到 $[0, 1]$ 区间，即为 CTR 预测分数。

**DeepFM 相对于其他模型的优势**：

- 相对于 LR（Logistic Regression）：LR 只能建模一阶特征交互，DeepFM 通过 FM 和 DNN 能够建模任意阶的交互。
- 相对于 Wide & Deep：Wide & Deep 需要人工设计 Wide 部分的特征交叉，DeepFM 的 FM 部分自动学习所有一阶和二阶交互，无需人工设计。
- 没有 FM 部分的 Deep 模型无法有效捕捉低阶交互，而 DeepFM 的 FM 组件以极低的计算开销（$O(n \cdot k)$）弥补了这一不足。
- FM 和 DNN 共享 Embedding 层参数，减少了约一半的参数量，同时使得低阶和高阶信息能够相互促进学习。

#### 2.4.4 DeepFM-Attention 增强模型

标准 DeepFM 将所有特征一视同仁地输入模型，但实际上用户在推荐场景中的行为具有明显的**时序特性**。例如，一个用户近期浏览了多款运动鞋（浏览序列：运动鞋A → 运动鞋B → T恤 → 运动鞋C），推荐一双新的运动鞋D时，如果模型能够"注意到"其浏览序列中大量的运动鞋记录，应该对运动鞋D给出更高的 CTR 预测。

本系统实现的 **DeepFM-Attention** 增强模型引入了 **DIN（Deep Interest Network）风格的 Attention 机制**来处理用户的历史行为序列信息。

**Attention 机制的核心思想**是为候选商品和用户历史行为序列中的每个商品计算一个"注意力权重"——权重越高说明该历史商品对当前候选商品的 CTR 预测越重要。最终用一个加权求和的向量来表示用户的历史兴趣，该向量与 DeepFM 的原始输出拼接后再进行预测。

具体实现步骤：

```
第一步：序列特征提取
  - 从用户行为历史中提取最近 20 个行为的商品
  - 每个商品的 embedding 向量作为序列中的一个元素

第二步：注意力权重计算
  attention_score_i = MLP([target_emb, history_emb_i, target_emb - history_emb_i, target_emb × history_emb_i])
  - MLP 是一个 3 层全连接网络，输出标量注意力分数
  - 将候选商品 embedding 与历史商品 embedding 做差和乘积，
    是为了捕捉"差异"和"共性"两种不同维度的信息

第三步：softmax 归一化
  attention_weight_i = softmax(attention_score_i) = exp(attention_score_i) / Σ exp(attention_score_j)

第四步：加权聚合
  attention_output = Σ attention_weight_i × history_emb_i

第五步：最终预测
  final_input = concat([DeepFM_output(32维), attention_output(16维)])
  final_output = sigmoid(MLP(final_input))
```

注意力权重计算的 softmax 归一化公式为：

$$
\text{attention\_weight}_i = \frac{\exp(\text{attention\_score}_i)}{\sum_{j} \exp(\text{attention\_score}_j)}
$$

加权聚合公式为：

$$
\text{attention\_output} = \sum_i \text{attention\_weight}_i \times \text{history\_emb}_i
$$

这一增强使得模型不仅能够利用用户和商品的统计特征，还能够捕捉用户**行为序列中的时序兴趣模式**，显著提升了排序精度。

#### 2.4.5 排序服务的调用流程

排序阶段的调用流程跨越两个微服务——Java 端的 recommendation-service 和 Python 端的 recommendation-rank-service。

```
Step 1: 特征构建（Java端）
  ├─ 从 MySQL 查询用户特征（行为统计、偏好）
  └─ 从 product-service 批量查询候选商品的商品特征

Step 2: 特征验证（Java端）
  └─ RankClientService.validateFeatures():
       - 检查候选商品的特征覆盖率
       - 如果覆盖率 < 50%：拒绝调用排序服务，降级回原始候选列表

Step 3: 远程调用（Java端 → Python端）
  └─ POST http://recommendation-rank-service:8010/rank/simple
       - Header: X-API-Key: <api_key>
       - Timeout: 5秒

Step 4: 模型推理（Python端）
  ├─ DeepFMAttentionRanker.rank():
  │    - 批量特征预处理（分桶编码、数值归一化）
  │    - PyTorch 模型推理（GPU/CPU 自适应）
  │    - 按 CTR 分数降序排序
  └─ 返回 {user_id, ranked_items: [{item_id, score}]}

Step 5: 结果处理（Java端）
  ├─ 接收排序结果，按 item_id 匹配原始候选
  ├─ 调用失败或超时时：降级回原始候选列表
  └─ 继续后续的多样性打散步骤
```

这种跨语言的微服务设计充分利用了各自技术栈的优势：Java 适合处理复杂的业务逻辑和 I/O 操作，Python 在深度学习模型的开发和迭代上具有无可比拟的生态优势（PyTorch、scikit-learn 等）。

### 2.5 步骤五：推荐结果后处理

排序完成后得到的推荐列表按 CTR 分数降序排列，直接返回给用户也是一种可行方案。然而，直接返回排序结果可能存在两个问题：**多样性问题**——如果推荐列表中的商品高度同质化（如前 10 个商品全是同一类目的手机），用户很快就会感到审美疲劳，探索欲望降低；**可解释性问题**——如果推荐结果没有附带任何解释，用户可能会对推荐结果感到困惑，降低信任度。因此，后处理阶段通过多样性打散和推荐理由生成来提升推荐结果的整体质量。

#### 2.5.1 多样性打散

**多样性打散**（Diversity Shuffling）是推荐系统中常被忽视但极为重要的环节。相关研究表明，适度的多样性能够显著提升用户的长期留存率和满意度——虽然短期 CTR 可能略有下降，但用户不会因为推荐结果过于单调而产生"审美疲劳"。

**类目打散策略**是最基础也是最有效的多样性控制手段。系统规定：同一类目的商品在推荐列表中最多连续出现 `maxConsecutiveSameCategory = 2` 次。当连续出现第 3 个同类商品时，系统会向后寻找第一个不同类目的商品进行**局部位置交换**。

举例说明：假设排序结果为 `[手机A, 手机B, 手机C, 服装A, 电脑A, 手机D, ...]`，其中手机连续出现了 3 次（位置 1、2、3），违反了打散规则。系统向后搜索，找到第一个非手机商品（服装A，位置 4），将其与位置 3 的手机C 交换，得到 `[手机A, 手机B, 服装A, 手机C, 电脑A, 手机D, ...]`。此时手机最多连续出现 2 次，打散完成。

之所以采用"局部交换"而非"全局随机打散"，是因为完全随机打散会严重损害排序阶段好不容易建立的相关性排序。局部交换策略在保证多样性的同时，最大程度地保留了排序算法的有效性。

**多维度打散**在类目打散的基础上进一步引入了品牌和价格维度，并使用 **MMR（Maximal Marginal Relevance，最大边际相关）算法**在相关性和多样性之间寻求最优平衡：

$$
\text{MMR\_score} = \lambda \times \text{relevance} - (1 - \lambda) \times \text{diversity}
$$

其中：
- $\text{relevance}$：商品的 CTR 预测分数（来自排序阶段，范围 0-1）
- $\text{diversity}$：多样性惩罚
  $= 0.3 \times \text{同类目商品已出现次数} + 0.2 \times \text{同品牌商品已出现次数} + 0.1 \times \text{同价格区间商品已出现次数}$
- $\lambda = 0.6$（可配置）
  - $\lambda$ 越接近 1：越注重相关性（排序分数高的商品优先）
  - $\lambda$ 越接近 0：越注重多样性（尽量打散不同类目/品牌/价格）

**智能跳过机制**：系统会先计算推荐候选池中最大类目的商品占比。如果该占比超过 60%，说明候选池本身就与用户偏好高度一致——用户近期大量浏览了手机类商品，候选池中手机类商品自然占多数。这种情况下强行打散反而会损害推荐效果。智能跳过机制判断到这种情况后，会跳过打散步骤直接返回原始排序。

**多样性指标的量化**：系统还提供了多样性指标的计算和展示接口，帮助量化评估推荐结果的多样性水平：

$$
H_{\text{category}} = -\sum_{c \in C} p(c) \times \log_2 p(c)
$$

其中 $p(c)$ 为推荐列表中类目 $c$ 的占比。熵越高，说明类目分布越均匀，多样性越好。例如，`[手机, 手机, 服装, 手机, 电脑]` 的熵高于 `[手机, 手机, 手机, 手机, 手机]`。

$$
\text{类目覆盖率} = \frac{\text{推荐列表覆盖的类目数}}{\text{全站总类目数}}
$$

品牌熵、价格方差等指标类似。

#### 2.5.2 推荐理由生成

**推荐理由**（Explainable Recommendation）是为了提升用户对推荐结果的信任度和透明度。用户看到一条推荐"无线降噪耳机"时，如果同时能看到推荐理由"与你近期浏览的蓝牙耳机相似"，会更容易接受这条推荐并产生点击行为。实验表明，带有推荐理由的推荐列表比不带理由的列表具有更高的点击率和转化率。

系统的推荐理由生成规则如下：

| 判断条件 | 推荐理由 |
|---------|---------|
| 商品与用户历史浏览的同类目商品相似度高（ItemCF 相似度 > 0.5） | "与你近期浏览的商品相似" |
| 商品属于用户偏好类目 Top1 | "符合你偏好的商品类目" |
| 商品来自热门召回通道 | "当前热门推荐" |
| 商品通过 ItemCF 协同过滤推荐且得分较高 | "为你精选推荐" |

这些判断依据均来自推荐链路中已有的中间结果——ItemCF 的相似度矩阵、用户偏好类目、热门召回通道标识等，无需额外计算。

### 2.6 步骤六：结果缓存

推荐结果被写入 Redis 多级缓存体系，这是推荐系统性能优化的关键环节。

**个性化推荐缓存**：`recommendation:personal:{userId}` → TTL = 2 小时。选择 2 小时的缓存时间经过仔细权衡：时间过短（如 5 分钟）会导致缓存频繁失效、增加数据库和排序服务的压力；时间过长（如 24 小时）则会导致推荐结果无法及时反映用户最新的兴趣变化。

**热门商品缓存**：`recommendation:popular:decay-0.95:all` → TTL = 1 小时。由于热门商品的计算基于全量用户行为数据，变化相对缓慢（不会出现分钟内剧烈波动），1 小时的缓存时间是合理的。

**ItemCF 相似度矩阵缓存**：`recommendation:similarity:v1:all` → TTL = 24 小时。相似度矩阵是计算密集型产物（涉及全量用户-商品交互数据的遍历），24 小时的缓存可以显著降低计算资源消耗。

**缓存失效策略**：采用**写时失效（Write-Through）**模式。当用户产生新的行为（浏览、点击、加购、购买等）时，系统会立即删除该用户的个性化推荐缓存和相关的相似度矩阵缓存，确保下次请求能够获取到最新的推荐结果。

### 2.7 步骤七：最终返回与展示

`RecommendationController` 将最终的推荐结果封装为 JSON 响应返回给前端。一个典型的推荐响应格式如下：


## 第三章 用户行为驱动的推荐引擎更新

### 3.1 行为数据管道的整体设计

用户在前端与推荐结果产生交互（浏览、点击、加购、收藏、购买）后，这些行为数据会通过数据管道流入推荐系统的各个模块，驱动推荐引擎的持续学习和优化。

`POST /api/recommendation/behavior` 接口是行为数据的统一入口。调用时系统会同时触发多个下游处理，形成一个"一次写入，多处消费"的数据流：

```
用户行为 → RecommendationService.recordBehavior()
    │
    ├─ ① 保存到 MySQL user_behavior 表（持久化存储，支持离线分析）
    ├─ ② 更新 Redis 用户已交互集合（推荐时过滤已交互商品）
    ├─ ③ 清除推荐缓存（保证下次推荐获取最新结果）
    ├─ ④ 触发用户画像更新（增量更新 Redis + 标记脏数据）
    ├─ ⑤ 触发在线学习记录（写入 Redis Stream + 更新实时 CTR 统计）
    └─ ⑥ 触发增量 ItemCF 更新（更新相似度矩阵的增量部分）
```

### 3.2 在线学习机制

#### 3.2.1 为什么需要在线学习

传统的推荐模型训练采用**离线批量训练**（Offline Batch Training）模式：收集一段时间的用户行为数据，进行特征工程和模型训练，部署上线后模型参数固定不变，直到下一次重新训练时才会更新。

然而，用户的兴趣和商品的热度都是动态变化的。离线训练的模型会逐渐"老化"——上周训练的模型参数无法反映本周用户兴趣的最新变化。在线学习（Online Learning）技术正是为了解决这一问题——在模型上线后持续接收用户的实时反馈（曝光、点击数据），以小步快跑的方式不断更新模型参数，让模型能够持续适应用户兴趣的变化。

#### 3.2.2 在线学习的数据管道

本系统的在线学习采用**Redis Stream**作为消息中间件，实现事件驱动的增量更新架构。

**数据采集阶段**：当用户点击推荐商品时，行为数据不仅写入 MySQL（用于离线分析），还会通过 `OnlineLearningService.recordBehaviorEvent()` 写入 Redis Stream。Redis Stream 是一种持久化的消息队列，支持消息的按序消费和消费者的故障恢复。

**定时消费阶段**：系统每分钟执行一次定时任务（`@Scheduled(fixedDelay = 60000)`），从 Redis Stream 中读取待处理的事件，构建训练样本并触发增量学习。

**样本构建**：在线学习的训练样本与离线训练有所不同——在线场景中无法精确知道用户没有看到的商品，因此需要采用特殊的采样策略。

最有效的策略是**曝光负采样**（Exposed but Not Clicked Negative Sampling）：从用户已经**曝光但未点击**的商品中采样作为负样本。这些商品至少满足一个关键条件——**用户看到了但没有点击**。与随机采样未曝光商品相比，曝光负采样的负样本更加"困难"，用户没有点击这些商品，一定是因为它们与用户兴趣存在某种不匹配，这种信号比随机采样更能训练模型区分正负样本的能力。

**模型增量更新**：增量学习的训练参数经过精心设计以保证稳定性：

```
- 学习率设为正常训练的 1/10（0.0001 vs 0.001）
  防止新数据导致的参数剧烈波动
- 训练轮次设为 3 epochs（正常训练通常 10-20 epochs）
  少量数据不需要多轮训练，否则容易过拟合
- 批量大小 64（远小于全量训练的百万级 batch）
  快速迭代，及时反映最新数据
- 样本数量门槛：最少 100 条才触发更新
  防止零星数据导致不稳定
- 样本数量上限：最多 5000 条/次
  防止突发流量导致的异常数据大量涌入冲击模型
```

#### 3.2.3 实时 CTR/CVR 统计

除了驱动模型更新，在线学习系统还维护了商品的**实时 CTR/CVR（点击率/转化率）统计**：

$$
\text{CTR}(\text{item}) = \frac{\text{24小时内点击次数}}{\text{24小时内曝光次数}}
$$

$$
\text{CVR}(\text{item}) = \frac{\text{24小时内购买次数}}{\text{24小时内点击次数}}
$$

这些统计存储在 Redis Hash 中（`itemCTR:{itemId}`），每小时自动过期并重新计算。实时 CTR 可用于：对曝光量足够但 CTR 持续走低的商品进行降权；对新上架但 CTR 迅速走高的商品进行加权；在推荐结果中过滤 CTR 过低的商品等。

### 3.3 用户画像的双轨更新机制

用户画像（User Profile）将用户的原始行为数据提炼为高层次的语义标签，为召回和排序提供丰富的用户特征输入。

#### 3.3.1 画像标签体系

**活跃度标签**反映用户的使用频率和参与程度：

| 标签值 | 判断条件 |
|-------|---------|
| 高活 | 30天内有行为且总行为数 > 50 |
| 中活 | 30天内有行为且 7 < 总行为数 ≤ 50 |
| 低活 | 30天内有行为且总行为数 ≤ 7 |
| 沉默 | 30天内无任何行为 |

**消费能力标签**反映用户的购买力水平：

$$
\text{score} = \text{buy\_count} \times 5 + \text{cart\_count} \times 2
$$

- $\text{score} \geq 10$ → 高消费（偏好高客单价商品）
- $\text{score} \geq 3$ → 中消费
- $\text{score} < 3$ → 低消费（偏好性价比商品）

**RFM 模型**是一种经典的用户价值评估框架（Recency, Frequency, Monetary）：

$$
\text{RFM\_score} = R \times 0.4 + F \times 0.3 + M \times 0.3
$$

其中各分量定义为：

$$
R = \max\left(0, 1.0 - \frac{\text{daysSinceActive}}{30}\right) \quad \text{// 越近活跃得分越高}
$$

$$
F = \min\left(1.0, \frac{\text{totalBehaviors}}{100}\right) \quad \text{// 行为数量越多得分越高}
$$

$$
M = \min\left(1.0, \frac{\text{buyCount}}{20}\right) \quad \text{// 购买次数越多得分越高}
$$

RFM 综合得分将用户分为：高价值用户（RFM ≥ 0.8）、活跃用户（0.5 ≤ RFM < 0.8）、潜力用户（0.2 ≤ RFM < 0.5）和沉默用户（RFM < 0.2）。

#### 3.3.2 双轨更新架构

用户画像的更新采用**双轨设计**，兼顾实时性和准确性：

**第一轨：实时增量更新**（行为触发，毫秒级响应）。当用户产生新行为时，`UserProfileService.updateProfileOnBehavior()` 会立即更新 Redis 中的用户画像计数器，并将用户标记为"脏数据"（`dirty:true`）。这种增量更新使得推荐系统能够快速感知用户兴趣的变化。

**第二轨：定时全量刷新**（每日凌晨 3 点）。此时系统读取所有被标记为"脏"的用户数据，从 MySQL 中重新拉取其全量行为记录，重新计算所有画像标签，并写回 Redis 和 MySQL。定时全量刷新用于修正增量更新过程中可能产生的累积误差。

**Redis + MySQL 双写**：Redis 作为高速读写层（TTL = 30 天，优先读写），MySQL 作为持久化存储层（异步双写，保证数据不丢失）。查询时优先从 Redis 读取，Redis 未命中时回退到 MySQL，再降级到实时计算。

## 第四章 系统服务间通信与安全保障

### 4.1 服务间通信协议

推荐系统内部各服务之间的通信采用 HTTP REST API 方式，遵循无状态通信原则。

**API Gateway → recommendation-service**：这是面向外部的唯一入口，所有请求都经过 JWT 认证后转发。

**recommendation-service → product-service**：推荐系统需要获取商品的类目、品牌、价格等信息。由于两个服务部署在同一个 Docker 内网中，不进行额外的 API 鉴权，通过 RestTemplate 发起 HTTP 调用，采用批量接口（`POST /api/product/batch`）减少网络往返次数。

**recommendation-service → recommendation-rank-service**：排序服务的调用是整个推荐链路中额外开销最大的远程调用之一（涉及 Java ↔ Python 进程间通信），系统进行了多项优化：调用前通过健康检查端点验证排序服务是否可用；使用 HTTP 连接池复用 TCP 连接；设置合理的超时时间（默认 5 秒）。

### 4.2 多层次安全保障

**第一层：API Gateway 的 JWT 认证**。所有面向外部的请求都需要经过 JWT Token 验证。网关负责解析 Token 并将认证后的用户 ID 以内部 Header 的形式传递给下游服务。

**第二层：推荐服务内部的身份校验**。Controller 在处理请求时，始终优先使用来自网关的 `X-Authenticated-User-Id` Header，而非前端传入的 URL 参数，从根本上防止了用户通过伪造 URL 参数来查询他人推荐结果。

**第三层：排序服务的 API Key 认证**。recommendation-service 调用 rank-service 时，需要携带 `X-API-Key` Header，防止未授权的外部调用访问敏感的模型推理接口。

**特征完整性保障（禁止假数据原则）**：整个推荐链路中任何无法获取真实数据的环节都明确失败或跳过，而非生成虚假的替代数据：

```
- 商品特征缺失 → 跳过该商品，不生成假特征
- 用户特征缺失 → 拒绝调用排序服务，降级回 ItemCF 结果
- 相似度矩阵为空 → 返回热门商品作为兜底
```

## 第五章 算法评测体系

### 5.1 离线评测

离线评测通过回放历史数据来评估算法的预测能力，其优势在于可以在不打扰用户的情况下进行大规模实验和快速迭代。

**留出法划分**：系统将用户行为数据按时间顺序划分为训练集（前 80%）和测试集（后 20%）。按时间划分而非随机划分，能够更好地模拟模型的真实应用场景（用过去的数据训练，预测未来）。

**核心评测指标**：

$$
\text{Precision@}K = \frac{\text{命中的正样本数}}{K}
$$

精确率衡量推荐列表 Top-K 中"准确"的程度。

$$
\text{Recall@}K = \frac{\text{命中的正样本数}}{\text{测试集总正样本数}}
$$

召回率衡量"用户真正感兴趣的商品中被推荐出了多少"。K 越大，Recall@K 通常越高（推荐越多，覆盖越广）。

$$
\text{DCG@}K = \sum_{i=1}^{K} \frac{\text{rel}_i}{\log_2(i+1)}
$$

其中 $\text{rel}_i = 1$（命中）或 $0$（未命中），$+1$ 避免 $\log_2(1) = 0$。

$$
\text{NDCG@}K = \frac{\text{DCG@}K}{\text{IDCG@}K}
$$

NDCG（归一化折扣收益累计）考虑了命中位置的影响——越靠前命中，收益越高，最佳值为 1.0（Top-K 全部命中）。

$$
\text{MRR} = \frac{1}{\text{第一个命中结果的位置}}
$$

如果第一个命中在第 3 位，$\text{MRR} = 1/3 \approx 0.333$。MRR 越接近 1，说明推荐列表越靠前的位置越容易命中。

$$
\text{HitRate@}K = \frac{\text{至少有一个命中的用户数}}{\text{总用户数}}
$$

命中率衡量"有至少一个有效推荐"的用户比例。

### 5.2 在线 A/B 测试

离线评测只能模拟历史数据，无法完全反映真实用户的行为偏好和系统的线上表现。因此，系统通过灰度发布机制实现了在线 A/B 测试。

在线 A/B 测试的核心指标为：

$$
\text{CTR} = \frac{\text{用户点击次数}}{\text{推荐曝光次数}}, \quad \text{加购率} = \frac{\text{加购次数}}{\text{推荐曝光次数}}, \quad \text{下单率} = \frac{\text{下单次数}}{\text{推荐曝光次数}}
$$

$$
\text{GMV提升} = \frac{\text{灰度组人均GMV} - \text{对照组人均GMV}}{\text{对照组人均GMV}} \times 100\%
$$

在进行 A/B 测试结论时，需要注意统计显著性——只有当灰度组指标持续显著优于对照组（通常需要 95% 置信区间的假设检验确认非随机波动）时，才能判定新算法真正有效。

## 第七章 核心技术亮点总结

**亮点一：两阶段推荐范式的工程实践**。系统成功落地了"多路召回 + 精排"的两阶段设计。召回层通过四条互补通道保证了候选集的多样性和覆盖面（ItemCF 协同过滤保证个性化、热门召回保证大众化、同类目召回保证精准性、TF-IDF 内容召回解决冷启动）；排序层通过 DeepFM 模型实现了精细化的个性化 CTR 预估。这种设计在计算效率和推荐效果之间取得了良好的平衡。

**亮点二：多通道互补的召回策略**。四条召回通道相互补充、相互兜底。ItemCF 基于协同过滤的"人以群分"原理挖掘个性化偏好；热门召回利用群体的智慧提供稳健推荐；同类目召回精准匹配用户的偏好类目；TF-IDF 内容召回利用商品标题的语义相似性解决新用户和新商品的冷启动问题。四条通道缺一不可，共同构成了完整的召回覆盖体系。

**亮点三：增量 ItemCF 的 $O(n \cdot k)$ 优化**。传统 ItemCF 的全量重算复杂度为 $O(n^2)$，本系统通过增量更新机制将复杂度降低到 $O(n \cdot k)$（$k$ 为平均邻居数）。当用户产生新行为时，仅更新相关局部相似度，定时合并回主矩阵，在保证相似度准确性的同时大幅降低了计算开销。

**亮点四：DeepFM 与 DeepFM-Attention 双模型体系**。DeepFM 同时建模低阶特征交互（FM 部分，$O(n \cdot k)$ 复杂度）和高阶特征交互（DNN 部分），无需人工设计特征交叉。DeepFM-Attention 在此基础上引入 DIN 风格的 Attention 机制，捕捉用户行为序列中的时序兴趣模式，进一步提升了排序精度。

**亮点五：用户画像双引擎架构**。Redis + MySQL 双写策略兼顾了读写性能和持久化需求。实时增量更新（行为触发，毫秒级响应）确保画像数据能够快速反映用户兴趣的变化；定时全量刷新（每日凌晨，精确重建）修正增量更新的累积误差。双轨设计在实时性和准确性之间取得了平衡。

**亮点六：完善的灰度发布基础设施**。一致性哈希分组保证了用户体验的稳定性（用户分组 7 天内不变）；HyperLogLog 以极低内存（约 12KB）实现高精度的独立访客统计；CTR/加购率/下单率实时对比为算法优化提供了数据驱动的决策依据。这套基础设施使得新算法的上线做到了可灰度、可监控、可回滚。

**亮点七："禁止假数据"的工程质量标准**。整个推荐链路中任何无法获取真实数据的环节都明确失败或跳过，而非生成虚假的替代数据。这一设计原则从根本上保证了推荐质量的可控性和可预期性。

**亮点八：MMR 多样性打散算法**。通过可配置的 $\lambda$ 参数在相关性和多样性之间灵活平衡，智能跳过机制避免了过度打散损害推荐相关性。既避免了推荐结果的同质化，又不会牺牲排序算法的有效性。
