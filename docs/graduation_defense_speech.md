## 二、 核心突破一：高并发秒杀引擎的设计与压测验证（约 3 分钟）

【**切换 PPT：秒杀系统架构图**】

### 2.1 问题与挑战

秒杀场景的核心矛盾是：成千上万的用户在同一秒涌入，但库存可能只有几百件。如果直接用数据库的悲观锁 `SELECT ... FOR UPDATE` 扣库存，MySQL 在高并发下会因为行锁争抢导致连接池耗尽、响应超时，最终整个系统雪崩。

### 2.2 我的解决方案：三道防线

我设计了一套严密的三级削峰架构：

**第一道防线：网关层令牌桶限流。**
在 Spring Cloud Gateway 上，我配置了基于 Redis 的 `RequestRateLimiter`，以 IP 为维度执行令牌桶限流（200rps/IP）。恶意刷单流量和超量请求直接在网关层以 **HTTP 429** 快速拒绝，根本不会到达后端。

**第二道防线：Redis Lua 脚本原子扣减——这是核心。**

【**切换 PPT：展示 Lua 脚本核心代码段**】

我没有用常规的"先查后扣"分步操作，而是编写了一段 **64 行的 Redis Lua 脚本**，将以下五步操作合并为一次原子执行：

```
步骤 1：检查用户是否已下单 → 幂等保障（防重复抢购）
步骤 2：检查库存 key 是否存在 → 防止未初始化
步骤 3：检查库存是否充足 → 防超卖（第一道检查）
步骤 4：分布式限流检查 → 用户+商品双重维度
步骤 5：DECRBY 原子扣减 → 扣完后二次检查 newStock ≥ 0
         如果 < 0 则立即 INCRBY 回滚 → 防超卖（第二道检查）
```

这段脚本有 **5 个不同的返回码**：`1` 表示成功，`-1` 重复下单，`-2` 库存不足，`-3` 未初始化，`-4` 限流拒绝。这些返回码让前端能精确区分失败原因，给用户不同的提示。

**为什么不用 Redisson 分布式锁？** 因为 Lua 脚本在 Redis 内部单线程串行执行，没有任何网络 IO 和锁竞争的开销；而 Redisson 分布式锁涉及多次 Redis 请求（加锁 → 业务 → 释放锁），在几千并发下依然会成为瓶颈。

**第三道防线：Redis Stream 异步削峰。**
Lua 脚本扣减成功后，我不直接写 MySQL，而是将订单事件写入 **Redis Stream** 消息队列。下游由 Consumer Group 多实例消费，以数据库能承受的速率慢慢持久化入库。消费失败的消息进入**死信队列（DLQ）**，并触发**库存补偿**逻辑（INCRBY 回滚 Redis 库存 + 删除用户秒杀记录）。

### 2.3 真实压测数据

【**切换 PPT：压测结果对比表**】

以下是我使用自研的 k6/Node.js 压测脚本在 **3000 请求、300 并发、1000 库存** 条件下的实测数据：

| 指标 | 直连秒杀服务 (8005) | 经网关限流 (8080) |
|------|---:|---:|
| **RPS（吞吐量）** | **2412 req/s** | **2710 req/s** |
| **P50 延迟** | 64 ms | 52 ms |
| **P95 延迟** | 452 ms | 439 ms |
| **P99 延迟** | 476 ms | 464 ms |
| 成功数 | 1000（= 库存） | 537（被限流拦截） |
| 失败原因 | 库存售罄 | HTTP 429 限流 |
| **超卖检查** | **通过（0 超卖）** | **通过（0 超卖）** |

两个关键结论：
1. **单机 Docker Desktop 下吞吐量达到 2710 RPS**，经网关场景因为快速拒绝了大量无效请求，整体吞吐反而更高——这恰恰证明了限流保护的价值。
2. **零超卖、零死信**。压测结束后等待 45 秒，MySQL 的 `order_info` 表恰好有 1000 条记录，Redis Stream 的 pending 和 lag 均为 0——**从 Lua 扣减 → Stream 入队 → Consumer 消费 → MySQL 落库，全链路库存一致性 100%。**

## 三、 核心突破二：工业级深度学习推荐系统（约 3 分钟）

【**切换 PPT：推荐系统分层漏斗架构图**】

### 3.1 为什么不能只用 SQL 查询热门商品？

大部分毕设的"推荐"其实就是一条 `ORDER BY sales DESC`。这种方式有两个致命问题：
- 它推给所有人的结果一模一样，毫无个性化可言；
- 新商品和长尾商品永远得不到曝光（马太效应）。

因此，我完整复刻了工业界的**召回-排序两阶段漏斗**。

### 3.2 召回层：四路并行，Java 端毫秒级筛选

在 Java 端的 `recommendation-service` 中，我实现了**四条互补的召回通道**：

1. **ItemCF 协同过滤召回（80 个候选）**：从 MySQL 加载最近 50,000 条用户行为，按行为类型赋予不同权重（购买=8, 加购=4, 点击=2, 浏览=1），并引入 `0.95^daysAgo` 的时间衰减因子。然后基于加权余弦相似度计算物品相似矩阵，其中包含活跃用户降权（`1/log(1+|I_u|)`）和热门偏差惩罚（`1/log(10+avgPop)`），解决了"所有商品都与爆款相似"的问题。
2. **热门商品召回**：考虑时间衰减的全局热度排序。
3. **同类目热门召回**：分析用户最近 500 条行为记录确定偏好类目，70% 候选来自偏好类目，30% 来自其他类目保证多样性。
4. **TF-IDF 内容相似度召回**：用 2-gram/3-gram 中文分词构建商品标题的 TF-IDF 向量，余弦相似度匹配——专门解决冷启动问题。

四路召回合并后，候选池上限控制在 **120 个商品**。

### 3.3 精排层：DeepFM-Attention 深度学习模型

候选集确定后，Java 端通过 HTTP + API Key 鉴权将商品 ID 和用户画像发送给独立部署的 Python 端 `recommendation-rank-service`。

【**切换 PPT：DeepFM 模型架构图**】

我实现的排序模型是 **DeepFM-Attention**，包含三大组件：
- **FM 组件**：通过数学恒等变换将二阶特征交互从 O(n²·k) 降低到 **O(n·k)** 的复杂度，自动捕捉所有特征对的交叉效应；
- **DNN 组件**：两层全连接网络（128→64→32），配合 BatchNorm + Dropout(0.5) 学习高阶非线性特征交互；
- **Attention 组件（DIN 风格）**：提取用户最近 20 个行为商品的 Embedding 序列，为候选商品与每个历史商品计算注意力权重，用加权聚合的向量捕捉用户的时序兴趣模式。

### 3.4 真实模型评测数据

【**切换 PPT：模型效果对比表**】

| 数据源 | 模型 | AUC | 备注 |
|--------|------|-----|------|
| 合成数据 5000 样本 | DeepFM 基线 | 0.5252 | 仅验证流程跑通 |
| **真实行为数据 78K** | **DeepFM-Attention + 曝光负采样** | **0.9668** | **Accuracy=0.93** |

从 AUC 0.52（约等于随机）到 **AUC 0.97**，这充分说明了真实用户行为数据和曝光负采样训练策略的价值。

此外，三种召回算法的离线 Top-10 对比：

| 算法 | NDCG@10 | HitRate@10 |
|------|---------|------------|
| Popular 基线 | 0.033 | 0.06 |
| **ItemCF (binary)** | **0.069** | **0.12** |

ItemCF 相对 Popular 基线，**HitRate@10 提升 100%，NDCG@10 提升 109%**。

### 3.5 灰度发布与 A/B 实验

我没有直接全量上线 DeepFM，而是设计了基于一致性哈希的灰度分组机制 `hash(userId) % 100 < grayRatio`，保证同一用户 7 天内始终落在同一组。核心指标（CTR/加购率/下单率）通过 Redis **HyperLogLog** 统计（每指标仅占约 12KB 内存），支持灰度组与对照组的实时效果对比。

同时，我还实现了完整的在线学习管道：用户行为通过 Redis Stream 实时上报 → 曝光负采样构造训练样本 → 以正常学习率 1/10 的微小步长（lr=0.0001）、3 个 epoch 进行增量更新——防止新数据冲击导致模型震荡。

## 四、 核心突破三：大模型 Agent 的全链路流式穿透与安全工程（约 2 分钟）

【**切换 PPT：Agent 架构 + SSE 链路图**】

### 4.1 解决 SSE 流式数据被网关阻塞的工程难题

接入大模型 API 本身不难，真正的挑战是在**多层微服务代理链路**下实现流畅的流式传输。

我最初联调时遇到了一个非常棘手的问题：大模型的回复是逐字输出的 SSE 流，但经过 Spring Cloud Gateway 代理后，网关的默认缓冲机制会把所有流式数据攒到最后一次性吐出，前端界面会假死十几秒然后突然出现一大段文字。

为此我逐层排查并修复了全链路的三个阻塞点：
1. **Python FastAPI 后端**：在 SSE 响应头中强制注入 `X-Accel-Buffering: no`、`Cache-Control: no-cache`；
2. **Spring Cloud Gateway**：在 agent 路由中配置透传这些响应头，禁用网关内部缓冲；
3. **前端 Nginx + Vue3**：在 nginx.conf 中显式关闭 `proxy_buffering off`，在 Vue 中放弃 Axios 改用原生 Fetch API 的 `ReadableStream` 逐字解析 `text/event-stream` 协议。

这才实现了真正类似 ChatGPT 的丝滑打字机体验。

### 4.2 防御大模型幻觉的 SQL Guard 安全层

【**切换 PPT：SQL Guard 拦截流程图**】

Agent 不是闲聊机器人——它通过 **Tool Calling** 实时操作后端 API 查库存、查订单、分析数据。但大模型存在幻觉风险，万一它生成了一条 `DROP TABLE` 怎么办？

为此，我在 Python 侧实现了一套基于 **sqlparse 抽象语法树** 的 `sql_guard` 校验拦截器，执行五道检查：
1. **禁止多语句**：`sqlparse.split()` 拆分后只允许 1 条；
2. **强制 SELECT**：解析 AST 首 token，`ttype != DML` 或 `value != 'SELECT'` 直接拒绝；
3. **写操作关键字正则黑名单**：正则扫描 INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER 等 18 种写操作关键字；
4. **表白名单校验**：正则提取 FROM/JOIN 后的表名，不在 9 张允许表内的一律拒绝；
5. **自动注入 LIMIT 200**：即使大模型忘记了 LIMIT，系统自动追加上限 500 的 LIMIT 防止全表扫描。

每一层都是独立的安全壁垒，任何一层拦截就终止执行——纵深防御，死守数据安全底线。

## 💡 附：评委高频技术追问与高分应对策略

### Q1：你的 Lua 脚本为什么要做两次超卖检查？一次不够吗？

> **回答**：好问题，老师。第一次检查是在扣减之前（`stock < quantity` → return -2），这是为了快速拒绝明显库存不足的请求，减少无效的 DECRBY 操作。第二次检查是在 DECRBY 之后（`newStock < 0` → INCRBY 回滚 → return -2），这是极端并发场景下的保护——虽然 Lua 脚本在 Redis 内部是单线程的，但我为了严谨性加了兜底检查。实际压测中，3000 并发 300 并发度的场景下从未触发过第二次检查的回滚，但工程上这种防御性编程是必要的。

### Q2：DeepFM 的 AUC 0.97 是不是过拟合了？

> **回答**：这个数据确实看起来很高，我在报告中也标注了。有两个原因：第一，我使用了**曝光负采样**策略，即从用户"看到但没点击"的商品中构造负样本，这比随机负采样难度更低，所以 AUC 会偏高；第二，训练数据有 78K 条真实行为记录，特征关联性较强。对比基线：纯合成数据的 AUC 只有 0.52，说明模型确实从真实数据中学到了有效的特征交叉模式。后续如果投入更大规模数据并改用更严格的时间切分评估（Time-based Split），AUC 数值会有所回落，但相对趋势是可信的。

### Q3：如果 Redis 宕机了，秒杀库存数据怎么办？

> **回答**：这是"缓存一致性"的经典问题。我的方案采用的是"最终一致性"模型——Redis 是库存的权威源，MySQL 通过异步消费同步。如果 Redis 宕机，当前秒杀活动确实会中断。我的补偿机制是：第一，Redis 开启了 RDB 持久化，宕机重启后可以恢复大部分数据；第二，`seckill-service` 的 `getActiveSeckillProducts()` 方法在 Redis 库存 key 不存在时会自动从 MySQL 的 `available_stock` 字段重新加载——这是一个懒加载兜底逻辑。在生产环境中，还应该加上 Redis Sentinel 或 Cluster 做高可用，这是我论文中"后续工作"部分提到的。

### Q4：为什么推荐系统要用 Java + Python 两种语言？维护成本不高吗？

> **回答**：确实增加了复杂性，但收益大于成本。召回层涉及大量的数据库查询、缓存操作和业务规则判断，Java 的 Spring 生态在这方面非常成熟；精排层需要 PyTorch 做模型推理，Python 的深度学习生态是 Java 无法替代的。两个服务通过 HTTP + API Key 鉴权通信，边界清晰。实际上这也是目前字节、阿里等一线大厂推荐系统的标准做法——Java 做在线服务，Python 做模型训练和推理。

### Q5：Agent 的 sql_guard 会不会被绕过？比如用注释或编码绕过？

> **回答**：我的 sql_guard 采用了多重防御策略。首先用 `sqlparse` 做 AST 级别的解析，比纯正则更可靠——它能正确处理注释、字符串内嵌关键字等情况。其次，即使 AST 解析被绕过，还有正则黑名单层做兜底（18 种写操作关键字）。最后，表白名单机制保证了即使 SELECT 通过了，也只能查 9 张允许的业务表。再加上 admin-service 本身的数据库账户也是只读权限——这是数据库层面的最后一道防线。纵深防御的思路是：没有任何单一层是万无一失的，但多层叠加后安全性会指数级提升。
